# Database Migrations

This directory contains SQL migration files following industry-standard practices for PostgreSQL database migrations.

**Note**: This is a development server and we are building the first iteration. Migration files may be modified directly as needed during development. Proper migration practices will be followed once we move to production.

## Migration Structure

Migrations follow the **separate up/down files** pattern, which is the most common standard used by tools like:

- `golang-migrate` (Go)
- `node-pg-migrate` (Node.js)
- `flyway` (Java)
- Custom migration runners

### File Naming Convention

- `NNN_description.up.sql` - Migration forward (applies changes)
- `NNN_description.down.sql` - Migration backward (rollbacks changes)

The numbering (`NNN`) ensures proper execution order.

## Separation of Concerns

Each file covers exactly one entity (one table, one set of related functions, or all enums).

## Running Migrations

### Using golang-migrate (recommended)

```bash
# Run all pending migrations
migrate -path ./db-migrations -database "postgres://user:pass@host/dbname?sslmode=disable" up

# Rollback last migration
migrate -path ./db-migrations -database "postgres://user:pass@host/dbname?sslmode=disable" down 1
```

### Using node-pg-migrate

```bash
# Run migrations
npm run migrate up

# Rollback
npm run migrate down
```

### Manual Execution

You can also execute `.up.sql` files manually in order using `psql` or your database client.

### Database Reset Script

For development purposes, a `reset.sql` file can be generated that will drop all database objects and recreate them from scratch. This is useful for clearing and rebuilding the database during development.

#### Generating the Reset Script

The reset script is automatically generated by the `generate-reset-sql.ts` script:

```bash
# From the backend directory (using npm script)
pnpm script:generate-reset-sql

# Or using tsx directly
npx tsx scripts/generate-reset-sql.ts
```

This will create `db-migrations/reset.sql` which contains:

1. All down migrations in reverse order (NNN → 000)
2. All up migrations in forward order (000 → NNN)
3. Wrapped in a transaction (BEGIN/COMMIT)

#### Using the Reset Script

**⚠️ WARNING: This will drop all tables, types, and functions! Only use in development.**

```bash
# Using psql
psql -d your_database_name -f db-migrations/reset.sql

# Or execute the file in your database client (pgAdmin, DBeaver, etc.)
```

The script uses `IF NOT EXISTS` and `IF EXISTS` clauses to be idempotent and safe to re-run, but it will still drop all existing data.

## Industry Standards Reference

- **Separate up/down files**: ✅ Standard (used by most tools)
- **Indexes with tables**: ✅ Common practice (keeps related objects together)
- **ENUMs in separate file**: ✅ Best practice (shared types)
- **Numbered migrations**: ✅ Standard (ensures order)
- **Down migrations**: ✅ Essential for rollbacks and testing

## Notes

- Always test migrations on a development database first
- Never modify existing migration files that have been run in production
- Create new migrations for schema changes instead of editing existing ones
- Indexes use `IF NOT EXISTS` to be idempotent and safe to re-run
- Each table migration includes its indexes for clarity and maintainability
